# 黑客松项目要求：CT 患者陪伴系统生态

## 文档范围与来源

本文按幻灯片右下角标注的页码，整理所提供的八张西门子医疗（Siemens Healthineers）幻灯片照片，即**第 2–9 页**。内容涵盖陪伴系统架构，以及 CT 成像工作流程中的五项功能挑战。

下文的要求与数值限制均来自幻灯片。要求编号为整理时添加，便于引用。架构描述用于交代背景，并不意味着团队必须实现其中的全部现有组件。幻灯片未说明的事项单独列为待确认问题。

原始幻灯片标有 **Restricted © Siemens Healthineers（受限资料，版权归西门子医疗所有）**。

## 1. 能力概览——第 2 页

陪伴系统需要在患者工作流程中支持情境理解与沟通。

| 能力 | 预期行为 | 幻灯片中的示例表述 |
| --- | --- | --- |
| 移动感知与引导 | 检测患者接近及移动，并据此提供引导。 | “现在有人在我面前。” |
| 问答服务 | 回答患者的问题。 | “检查需要 10 分钟。” |
| 患者身份识别 | 在整个工作流程中识别患者。 | “这仍然是同一个人。” |
| 房间状态检查 | 检查 CT 检查室的状态。 | “房间里没有其他人。” |
| 体位感知与引导 | 识别患者在检查床上的体位，并提供引导。 | “患者以头部朝向扫描仪的方向躺卧。” |

这些表述用于说明功能；其中的检查时长仅为示例，并非固定要求。

## 2. 陪伴系统生态——第 3 页

### 2.1 组件与技术背景

| 组件 | 作用 | 幻灯片列出的技术 |
| --- | --- | --- |
| ACU App | 操作人员界面，用于发送指令和工作流程。 | 浏览器/PWA、React、REST |
| ACU Server | 集成与通信枢纽，提供 API 网关。 | ASP.NET Core、WebSocket 与 REST、运行于 Linux 的 Docker |
| 机器人 / KettyBot App | 面向患者的陪伴交互界面。 | Kotlin / React Native |

### 2.2 通信流程

- 指令由 ACU App 通过 REST API 发送至 ACU Server，再通过 WebSocket 和 REST 发送至 Ketty Bot Pro。
- 状态与遥测数据通过同一平台返回。
- 机器人向服务器提供遥测数据和状态，服务器向操作人员应用提供遥测数据。

## 3. 组件视图——第 4 页

ACU 服务器硬件承载本地应用与服务平台。单一 API 网关提供统一入口和服务访问。

| 层次或分组 | 幻灯片列出的组件 |
| --- | --- |
| 用户交互终端 | ACU、工作站、候诊舱 |
| 界面 | ACU UI Web 应用、候诊舱 Web 应用 |
| 领域服务 | 房间状态检查器、患者验证器、患者健康计算器、患者移动检测器 |
| 图像来源 | 机器人（BOT）和摄像头 |
| 数据与输出 | 房间状态、患者数据、其他数据存储及输出 |

该架构强调**单一网关、模块化服务和本地处理**。

组件图中出现了“患者健康计算器”，但所提供页面没有给出该服务的详细要求。图中还包含一个未标注名称的数据存储，此处不对其用途作推定。

## 4. 持续患者检测与引导——第 5 页

### 目标

确保在整个工作流程中检测到正确的患者，并持续为其提供引导。

### 功能要求

| 编号 | 要求 |
| --- | --- |
| CDG-01 | 通过 API 网关/后端接收机器人提供的患者图像，用于登记患者。 |
| CDG-02 | 在 ACU 上识别患者，并验证引导过程保持连续。 |
| CDG-03 | 如果失去对患者的跟踪，通知 ACU 并触发纠正性引导。 |

### 限制条件

| 限制项 | 幻灯片规定的限制 |
| --- | --- |
| 内存 | **小于 2 GB** |
| 存储的患者数量 | **最近 2 名患者** |
| 反馈时间 | **不超过 3 秒** |
| 执行位置 | **本地 ACU** |

幻灯片没有定义反馈时间的计时起点与终点事件。

## 5. 问答服务——第 6 页

### 目标

回答患者的一般性问题，并提供清晰的背景说明，使患者了解情况并做好扫描准备。

### 功能要求

| 编号 | 要求 |
| --- | --- |
| HD-01 | 通过机器人采集患者的问题，并通过 API 网关/后端发送。 |
| HD-02 | 在 ACU 上运行模型，生成适当的回答。 |
| HD-03 | 将 ACU 的输出返回机器人，以便向患者输出回答。 |
| HD-04 | 机器人仅用于输入和显示；模型在本地 ACU 上执行。 |

**原文说明：** 幻灯片的“Respond（响应）”框以“ACU output is returned to the BOT for”结尾，句子未写完整。“向患者输出回答”是根据问答服务的目标及“机器人仅用于输入/显示”的限制推断的。

### 限制条件

| 限制项 | 幻灯片规定的限制 |
| --- | --- |
| 内存 | **4 GB** |
| 存储空间 | **4 GB** |
| 模型执行位置 | **本地 ACU** |
| 机器人职责 | **仅用于输入/显示** |

幻灯片没有给出响应时间目标、支持的语言列表或知识来源规范。

## 6. 患者身份识别：确保扫描的是正确患者——第 7 页

### 目标

只有成功识别并确认已登记患者的身份后，才允许启动扫描工作流程。

### 身份识别方式

| 方式 | 说明 |
| --- | --- |
| 人脸 | 基于图像进行匹配 |
| 二维码 | 已登记的二维码 |
| 语音 | 语音验证 |

幻灯片列出了这三种方式，但没有说明它们是可选方案，还是必须组合使用。

### 功能要求

| 编号 | 要求 |
| --- | --- |
| PI-01 | 在机器人端采集患者信息，并发送至 ACU。 |
| PI-02 | 在本地 ACU 上执行身份识别。 |
| PI-03 | 允许用户接受或拒绝身份识别结果。 |
| PI-04 | 只有在身份识别成功且完成确认后，才允许工作流程继续。 |
| PI-05 | 如果身份识别失败，要求重新识别，最多允许尝试 3 次，并保持工作流程被阻止的状态。 |

### 限制条件与流程放行条件

| 限制项 | 幻灯片规定的限制或行为 |
| --- | --- |
| 执行位置 | **本地 ACU** |
| 内存 | **小于 2 GB** |
| 患者数据保留范围 | **仅保留最近 5 名患者** |
| 尝试次数限制 | **最多 3 次** |
| 确认方式 | **用户接受/拒绝** |
| 流程放行 | **仅在确认后放行** |

幻灯片没有说明由谁执行确认、首次尝试是否计入 3 次限制，以及达到次数上限后应如何升级处理。

## 7. CT 检查室就绪状态检查——第 8 页

### 目标

在成像工作流程启动前，检测需要处理的异常物体、准备不充分或其他偏差。

### 功能要求

| 编号 | 要求 |
| --- | --- |
| RR-01 | **仅在房间无人时**执行就绪状态检查。 |
| RR-02 | 通过 API 网关/后端接收机器人提供的多张房间图像。 |
| RR-03 | 在 ACU 上使用房间就绪状态算法分析图像，并将预期应存在的设备纳入判断。 |
| RR-04 | 检测偏差，包括未知或不应出现的物体。 |
| RR-05 | 向 ACU UI 返回房间**已就绪/未就绪**的状态。 |
| RR-06 | 房间已就绪时允许启动工作流程；未就绪时阻止扫描启动。 |
| RR-07 | 支持准备/纠正操作，并在清除物体后由机器人重新检查。 |
| RR-08 | 在本地存储相关图像。 |

### 判断与纠正流程

1. 采集房间图像并评估就绪状态。
2. 如果已就绪，允许工作流程继续。
3. 如果未就绪，阻止扫描，并对房间进行准备或纠正。
4. 清除不应出现的物体，由机器人重新检查房间。
5. 在本地存储相关图像。

### 限制条件

| 限制项 | 幻灯片规定的限制或范围 |
| --- | --- |
| 内存 | **4 GB** |
| 存储空间 | **2 GB** |
| 房间人员状态 | **仅限无人房间** |
| 图像输入 | **机器人提供的多张图像** |
| 图像存储位置 | **本地** |

幻灯片没有说明预期设备清单、图像保留策略或具体的就绪判断标准。

## 8. 患者体位识别与引导——第 9 页

### 目标

在扫描开始前，检测需要纠正的患者移动或偏离预期体位的情况。

### 功能要求

| 编号 | 要求 |
| --- | --- |
| PP-01 | 生成预期患者体位的参考图。 |
| PP-02 | 接收摄像头图像，并持续跟踪患者移动。 |
| PP-03 | 将检测到的体位与可接受标准进行比较。 |
| PP-04 | 需要采取措施时通知 ACU。 |
| PP-05 | 引导患者调整体位，并在必要时阻止工作流程启动。 |
| PP-06 | 当体位符合可接受标准时，允许启动工作流程。 |

### 流程决策

| 体位评估结果 | 要求的行为 |
| --- | --- |
| 符合标准 | 允许启动工作流程。 |
| 不符合标准 | 引导调整体位，并阻止启动。 |

### 限制条件

| 限制项 | 幻灯片规定的限制或行为 |
| --- | --- |
| 执行方式 | **本地边缘执行** |
| 内存 | **4 GB** |
| 存储空间 | **2 GB** |
| 监测方式 | **持续监测** |
| 参考依据 | **预期体位参考图** |
| 通知对象 | **ACU** |

示意图中使用了天花板摄像头。幻灯片没有定义摄像头规格、可接受的移动/体位阈值，或参考图的获取方式。

## 9. 资源与行为限制汇总

以下按功能分别列出限制。幻灯片没有说明各服务是否共享内存和存储预算，也没有说明未带限定词的 4 GB 和 2 GB 数值是否为严格上限。

| 功能 | 页码 | 内存 | 存储空间 | 其他限制 |
| --- | --- | --- | --- | --- |
| 持续患者检测与引导 | 5 | < 2 GB | 未说明 | 最近 2 名患者；反馈 ≤ 3 秒；本地 ACU |
| 问答服务 | 6 | 4 GB | 4 GB | 模型在本地 ACU 上运行；机器人仅用于输入/显示 |
| 患者身份识别 | 7 | < 2 GB | 未说明 | 最近 5 名患者；最多尝试 3 次；用户确认；本地 ACU |
| 房间就绪状态检查 | 8 | 4 GB | 2 GB | 仅限无人房间；机器人提供多张图像；相关图像本地存储 |
| 患者体位识别与引导 | 9 | 4 GB | 2 GB | 本地边缘执行；持续监测；通知 ACU |

**注意区分患者数据保留数量：** 持续患者检测保留最近 **2** 名患者，而患者身份识别保留最近 **5** 名患者。

## 10. 需要向组织方确认的事项

以下是文档中尚未说明的事项，并非额外要求：

- 团队需要选择一个挑战实现，还是必须实现全部五项功能。
- 提交材料、代码仓库格式、演示要求、截止时间和评审标准。
- 可用硬件、数据集、预训练模型、参考图像和患者登记示例。
- API 端点、请求/响应数据结构、身份认证、事件格式和集成测试环境。
- 资源预算是按进程、按服务分配，还是共享；资源使用量如何测量。
- 准确率目标、置信度阈值、第 5 页反馈限制以外的延迟目标，以及失败处理规则。
- 身份识别方式的选择、执行确认的人员、尝试次数计算方式，以及识别失败后的升级处理。
- 患者数据和本地房间图像的具体保留与删除规则。
- 就绪判断标准、预期设备清单，以及可接受的体位/移动偏差范围。
